# Independent exact-source review: tps6598x SPMI transport (SN201202x)

Date: 2026-08-18. Reviewer: fable (offline, no rig). Reviewed artifact:
`patches/0001-usb-typec-tps6598x-add-SPMI-transport-for-T6040-SN20.patch`
as committed in `77fd00b` with its evidence
`evidence/2026-08-04-t6040-tps6598x-spmi-transport.md`. This is the
"independent exact-source review" that commit names as its first remaining
gate.

## Verdict

**Sound. The refactor is faithful, the paged regmap_bus matches the
live-proven access pattern, and the probe-time transaction envelope is inside
the sanctioned classes.** No blocking defect found. Three non-blocking
remarks and one enumerated sign-off list for CJ below.

## What was verified, claim by claim

**Refactor faithfulness (core.c).** `tps6598x_probe_common()` is the old
`tps6598x_probe()` with exactly the three transport-specific seams moved out
(match data, regmap construction, IRQ number) and every `client->…` use
rewritten onto `dev`/`tps->irq`. Diff-walked hunk by hunk: probe order,
error unwinding (`err_disconnect`/`err_unregister_port`/fwnode put), PM ops,
and remove are behavior-identical for the I2C path. `i2c_verify_client(dev)`
correctly returns NULL for the SPMI device, so `tps->i2c_protocol` stays
false and block I/O takes the plain-regmap path — the SPMI bus then sees one
whole logical register per call, which its paging requires.

**Module shape.** Single `module_init` (the old `module_i2c_driver` macro
expanded and extended); `spmi.o` links into the same `tps6598x` object via
`tps6598x-$(CONFIG_TYPEC_TPS6598X_SPMI) += spmi.o`, so `cd321x_data`,
`tps6598x_probe_common`, `tps6598x_regmap_config` and `tps6598x_pm_ops` are
shared without exports; the `#else` static-inline stubs keep the I2C-only
build unchanged. Kconfig: `bool`, `depends on TYPEC_TPS6598X && SPMI`.
Checked for the tristate/bool composition hazard — none: the objects join
one module regardless of =y/=m.

**The paged bus vs the live-proven protocol.** The select-then-window
sequence (`spmi_register_zero_write(reg)` → poll reg 0 for `reg` with
`BIT(7)` clear → payload chunks of ≤16 bytes through the window at `0x20`,
address advancing per chunk) matches `~/Code/m1n1-hpm2/src/t6040_hpm2.c`,
which passed live R2 against this exact hardware, and the AppleHPMARMSPMI
decode. All three SPMI APIs used exist in `include/linux/spmi.h`
(`spmi_register_zero_write`, `spmi_ext_register_read/write`,
`spmi_command_wakeup`). The regmap contract is honored: `max_raw_read/write`
deliberately unset so regmap never splits a wide logical register across bus
calls (a split would re-select at a wrong offset); regmap's own mutex
serializes complete select+window sequences, including against the poll
worker; `.read`/`.write`/`.gather_write` cover every path core.c uses
(`regmap_raw_read/write`, single-register reads). `reg_size != 1` is
rejected. Select-poll failure modes are fail-closed (-EIO on an unexpected
readback, -ETIMEDOUT after 100×1 ms, both matching the m1n1 budget).

**Probe envelope (the safety question).** At probe, in order: SPMI WAKEUP
(sanctioned, mirrors m1n1), regmap init (no traffic), `of_irq_get`
(EPROBE_DEFER propagated; polling fallback like I2C), then
`tps6598x_probe_common` → VID/mode/status reads, `cd321x_switch_power_state`
(SSPS→S0 — the live-proven ticket-095 write; skipped if already S0), typec
port registration, `TPS_REG_INT_MASK1` write. No role-swap 4CC is reachable
from probe. Confirmed in source: `SWDF/SWUF/SWSr/SWSk` live only in
`tps6598x_dr_set`/`_pr_set`, invoked by the typec class (sysfs) — nothing in
our images calls them.

## Non-blocking remarks

1. **"Mirrors, byte for byte, AppleHPMARMSPMI::readRegs" overstates.** Per
   the R3 boundary decode, Apple polls SPMI register `0x1f` after select;
   this driver polls register `0x00` readback — the m1n1-proven variant.
   Functionally validated on this hardware, but the comment should say
   "mirrors the m1n1-proven access" before any upstream submission.
2. **The DT is the entire safety gate.** The driver binds *any* node with
   the compatible, on any of the four PD controllers. The follow-on DT
   connector node must describe **right-port hpm2 only** (ADT-derived SID
   `0x0c` under `nub-spmi-a1`), or probe traffic reaches endpoints outside
   the reviewed envelope. This belongs in the DT-node review checklist.
3. **`usbc,sn201202x,spmi` as a compatible** is the ADT string, fine for
   bring-up, not a mainline-shaped binding ("Not submitted upstream as-is"
   already acknowledges this).

## Runtime SPMI transaction envelope — the list CJ signs off

Binding this driver to hpm2 authorizes, at runtime:

| When | Transaction | Class / precedent |
|---|---|---|
| probe | SPMI WAKEUP command | sanctioned (m1n1 R0 preamble) |
| probe | reads: VID 0x00, MODE 0x03, STATUS 0x1a, power state 0x20, PD/data status | R0 (reads) |
| probe | 4CC `SSPS`→S0 via CMD1/DATA1 (0x08/0x09), only if not already S0 | live-proven (ticket 095) |
| probe | `INT_MASK1` (0x16) write of `cd321x_data.irq_mask1` | **new** — first Wallace write to 0x16 |
| per event (IRQ or poll) | read `INT_EVENT1` (0x14); W1C to `INT_CLEAR1` (0x18); status reads | **new** — tipd takes event ownership at bind, exactly as the R3 boundary doc's route recommendation describes ("Linux's tipd takes ownership of both at bind") |
| never (unless userspace acts) | role-swap 4CCs via typec sysfs | out of scope; nothing invokes them |

The R3 boundary design's "never touch 0x14/0x16/0x18" rule was written for
the *hand-rolled m1n1* path; handing them to the bound upstream-shaped
driver is the alternative that same document recommends. The distinction —
and the two **new** rows above — is what CJ's sign-off should explicitly
cover, together with remark 2 (hpm2-only DT).
