# Review 5011: symmetric SIQ_CFG_EL1 experiment (m1n1 siq vs control, cow-report launcher) — PASS with three must-fixes

Date: 2026-10-25. Reviewer: claude (Mythos Wallace session), offline, host
only; nothing executed on the rig. Requested by Opus Wallace; package at
`c2a43b1`.

## Verdict

The experiment is the right one and the artifacts are what the ticket
says. The two m1n1 binaries differ in exactly one byte, the
`features_m4.siq_cfg` flag, and both already contain the single
`msr S3_4_C15_C10_4` that the flag gates; the payload is the reviewed 217
storage-free reproducer, byte for byte. Three must-fixes in the tooling
(the verify script cannot verify the siq build, the fault counter counts
every fault twice, the deadline is probably short), then run. On the run
count: 2 fresh boots per cell as the first pass is acceptable with the
ordering and escalation rule in §5.

## 1. The patch and the pair

`patches/m1n1-t6040-siq-cfg.patch` (`f62ad815…` = pin): adds
`.siq_cfg = true` to `features_m4` under `#ifdef T6040_SIQ_CFG`, nothing
else. With it, `init_cpu` (`chickens.c:233-237`, runs on every core from
`startup.c:206/228`) executes the existing `msr SYS_IMP_APL_SIQ_CFG_EL1, 2;
isb`, exactly what M1, M2 and M3 get today.

`linux-build-out/m1n1-siq-20261025/`: hashes equal the ticket pins
(`m1n1-siq.bin 7cbf67fe…`, `m1n1-control.bin bf4b2462…`, ELFs
`79f1f7f8…`/`183367ca…`). `cmp -l`: the `.bin`s differ in **one byte** at
offset `0x5d6b3`, siq = `1`, control = `0`; `nm` puts `features_m4` at
`0x5d6a4`, so the byte is field offset 15 of the struct, the `siq_cfg`
bool. The ELFs also differ in one byte. Both binaries contain exactly one
`MSR S3_4_C15_C10_4` encoding (`d51cfa8x`), so the write path is compiled
in identically and only the flag selects it. `spin_table` is at
`_base+0xdd290` in both (the 5010 verify tooling still applies). Both
`.bin`s are 1,097,728 B, a whole number of 16 KiB pages. Version string
`v1.6.0-wallace-80badc91` is present. Build logs are the same make output
apart from ordering; neither records `-DT6040_SIQ_CFG` (note 1).

**Write class:** one `msr` per core to a CPU-core IMP-DEF register that
m1n1 performs on every supported SoC; not PMU, SMC, SPMI, NVRAM, MMIO. The
ticket records it as a new class. Note that the siq variant changes
**two** things: secondaries 3 → 2 and the boot core 0 → 2. If siq removes
the fault, variant B (secondaries only, to 0 = iBoot's cpu0 value) is the
disentangling run, as the ticket already says.

## 2. Payload

`Image a9a2096f…`, `t6040-j614s-dcuart.dtb 30b01736…`,
`initramfs-cow-report.build1.cpio.gz de1a5cd7…` equal ticket 217's pins
and my 217 review. The initramfs `/init` runs
`/usr/local/bin/t6040-cow-repro.sh` four times with
`T6040_COW_RUN_BEGIN run=N` / `T6040_COW_RUN_END run=N` to kmsg and ends
with `T6040_COW_REPORT_END`; the reproducer is the 208 script (512 KiB
heap, 300 forks). No storage is mounted or written; the 217 artifact note
that its fault rate must be re-baselined still holds and is what the
control cells provide.

## 3. Launcher `scripts/t6040-run-cow-report.sh` (`a14522f0…` = pin)

Correct: refuses an existing run dir; checks the m1n1 hash prefix and the
three payload hashes before boot; `env -u EXTRA_BOOTARGS`, `RIG_ENFORCE=1`,
`BOOT_MAXCPUS=$N BOOT_IDLE=nop`, `CHAINLOAD_ATTEMPTS=1`; asserts
`maxcpus=$N ` in `dcuart-boot.log` (linux.py prints `Setting boot args:`
there, verified on an existing log); waits for `T6040_COW_REPORT_END` or
the deadline; prints one RESULT line.

**Must-fix A, double counting.** Every arm64 kernel fault prints both
`Unable to handle kernel …` and `Internal error: Oops`, and both the
`faults_total` grep and the per-run awk match both lines, so every fault
counts twice. Count one pattern (`Internal error: Oops` is the safer one;
`Unable to handle` also appears for the dump header) in both places.

**Must-fix B, deadline.** 208 measured "fault within ~40 s" per run at
maxcpus=2; a clean run of 300 forks is not faster than a faulting one,
and there are four runs plus boot. `DEADLINE=240` risks cutting a clean
siq boot short and reporting `report_end=0`, which would read as a fault.
Set 480 and record `waited=` so the first boots calibrate it. A boot that
dies at `unpack_to_rootfs` (the maxcpus=6 pattern) shows `report_end=0`
with `faults_total>0`; that is a valid result, not a deadline miss, and
the RESULT line already distinguishes the two.

Minor: faults before the first `T6040_COW_RUN_BEGIN` land under an empty
run key (`:N`); label that `boot` in the awk.

## 4. Verify step

**Must-fix C.** `scripts/t6040-run-sysreg-diff.sh` hardcodes
`M1N1_BIN=…/nvme-exfat-write-20261025/payload/m1n1.bin` and its
`7de07c71…` hash, so as written it chainloads the unpatched m1n1 and would
"verify" the wrong binary. Add `M1N1_BIN`/`M1N1_SHA256` overrides (or a
5011 copy) pointing at `m1n1-siq.bin 7cbf67fe…`, and expect
`SIQ_CFG_EL1 = 0x2` on cpu0, cpu1 and cpu5 (and `0x0`/`0x3`/`0x3` on a
control chainload if you want the negative control for the read path; one
extra proxy run, reads only).

## 5. Run count

205's rule is four runs per variant of the fresh-boot reproducer; the 217
artifact gives four in-boot runs per boot, which are not independent
(after a fault the kernel continues with a killed process). Accepting the
DebugUSB cost, do this:

1. Order: `control 6`, `siq 6`, `control 2`, `siq 2`, two boots each
   (8 boots + verify), control first in each pair so the rate the siq
   boots are compared against is measured the same day.
2. **If siq faults at all** in either cell, the result is negative at two
   boots; stop, no more boots needed for the claim.
3. **If siq is clean in both cells while control shows faults**, add two
   more boots per siq cell (4 fresh boots, the 205 rule on the cells that
   carry the claim) before writing anything stronger than "candidate".
   With control's per-boot rate `r`, `n` clean siq boots have chance
   `(1-r)^n` under the null; at 208's `r ≈ 0.5` that is 6 % at 4 boots,
   which is the evidential floor for a "mechanism candidate" line in
   NEXT_STEPS, not for "fixed".
4. If control is itself clean at maxcpus=2 (the 217 re-baseline risk),
   the maxcpus=2 cells say nothing and only the maxcpus=6 cells count.

## Notes

1. The build logs do not show the define; the one-byte diff is the proof,
   but write the exact `make` invocation for both builds into the 5011
   evidence so the provenance is reproducible without trusting the diff.
2. After the siq variant, the chainloaded m1n1 has written SIQ_CFG on
   cpu0 as well; the rollback proxy is unaffected (it does not start
   secondaries), so the recovery path is the usual one.
3. If siq removes the fault, do not promote the patch past "experiment"
   until variant B has run: the upstream-shaped change is "M4 gets
   `.siq_cfg` like every other generation", and the value (2 vs iBoot's
   0) should be argued from both results.
