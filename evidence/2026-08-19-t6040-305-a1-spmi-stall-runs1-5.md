# Ticket 305 runs 1–5: the PD image boots — except that any kernel access to the a1 SPMI controller hard-hangs the machine

Date: 2026-08-19. Agent: fable. Attended throughout (CJ photographing the
panel; the photos were the decisive instrument twice). Lease cycles all
released healthy; machine left at a quiescent rollback proxy.

## Where this leaves the VBUS experiment in one paragraph

The PD-enabled image (`Image-usb2pd.buildA`, `5a136710…`) is healthy: with
the `nub-spmi-a1` controller node disabled, run 5 boots all the way to the
i3 desktop with WiFi up, xHCI root hubs present, serial printk working, and
`tps6598x_module_init` returning in 23 µs. **Linux SPMI works on this SoC**
— the abbey PMU nvmem read over `nub-spmi0` succeeded (macsmc-rtc registered
`rtc0`, which requires the SPMI RTC-offset read; the first Linux-issued SPMI
transactions on T6040, in-envelope). What does not work: **the first kernel
MMIO access to the a1 controller (`0x309198000`) hard-hangs the machine** —
silently, unboundedly, until the un-pinged watchdog warm-resets. The same
driver on `nub-spmi0` (`0x509014000`) works. hpm2/VBUS therefore remains
blocked on understanding what makes the a1 block inaccessible from Linux.

## What each hypothesis did

1. **Missing controller `power-domains` (runs 1–2 → 3).** Real bug, real
   progress: adding `ps_nub_spmi0`/`ps_nub_spmi_a1` to the controller nodes
   moved the hang from the spmi-apple probe (0.15 s) to the first hpm2
   transaction (0.50 s). The kernel's own `always-on domain nub_ocla is not
   on at boot` line (run-1 photo) was the tell that nub domains arrive off.
2. **Gen3 register layout (run 3 analysis).** Refuted: m1n1's
   `regs_gen1_to_3` (status 0x00 / cmd 0x04 / reply 0x08) is byte-identical
   to the Linux driver's layout.
3. **Missing `ps_nub_spmi_ahb` parent on the a1 domain (run 4).** Refuted
   twice over: the run changed nothing, and the ADT pmgr table (parsed with
   m1n1's record layout) shows Apple gives `NUB_SPMI_A0/A1/A2` **no parent**
   — only `NUB_SPMI0..4` parent to `NUB_SPMI_AHB`. The dtsi edit was
   reverted for ADT fidelity. The ADT also confirms our pmgr offsets
   (`AHB=0x58, spmi0=0x60, a0=0x68, a1=0x70, a2=0x78`, group 3) are correct.
4. **`spmi_command_wakeup` NULL-op detour (analysis).** The Apple controller
   driver implements only `read_cmd`/`write_cmd`, no `.cmd` — the SPMI core
   NULL-checks and returns -EINVAL, so the probe's WAKEUP never reaches the
   part (harmless for a warm part; a correctness note for the driver).

## Live-system findings (run 5)

- `genpd` says **every nub domain is on**, `nub_spmi_a1` included — the
  kernel believes the block is powered, and it still stalls when touched
  (established by runs 3/4 under the same config).
- `tps6598x_module_init returned 0 after 23 usecs` with no device present —
  registration is innocent; the hang is inside the hpm2 probe's first
  controller access (`spmi_register_zero_write` → `writel` to CMD, or the
  first status `readl`; indistinguishable without instrumentation).
- `STRICT_DEVMEM` blocks `/dev/mem` reads of iomem — userspace MMIO probing
  is not available on this image (both spmi0 and a1 dd-reads returned zero
  bytes; no signal either way).
- Diagnostic-image caveats, by design: no trackpad firmware in this profile;
  keyboard also unresponsive in X on this boot (unexplained, out of scope
  here, does not affect the daily image).

## An inconclusive probe, recorded so nobody trusts it

From the rollback proxy I attempted `p.read32(0x509014000)` /
`p.read32(0x309198000)` (R0 controller status reads, the same class m1n1's
driver performs). m1n1 took a synchronous exception and the proxy died; the
full dump (ESR/FAR) scrolled off before capture. **This is NOT evidence
about the hardware**: the rollback m1n1's MMU map may simply not cover these
MMIO ranges (the July hpm2 work ran a custom m1n1 build), so the exception
is expected on unmapped addresses regardless of block state. Machine
recovered to a healthy proxy afterwards.

## What we now know, compactly

- Linux + apple-spmi + paged tps transport all work — proven on spmi0.
- The a1 block at `0x309198000` hard-stalls the AXI access from Linux, with
  pmgr reporting the domain on, offsets ADT-verified, and layout identical
  to the working controller.
- m1n1 read the same block fine in July (iBoot-warm, custom m1n1). Whether
  it still does today is unverified (see inconclusive probe).
- Remaining explanation space: something the a1 block additionally needs
  that iBoot leaves unset and macOS/AppleSPMIController sets (a clock-gate,
  queue/IRQ enable, or bridge config the numbered controllers do not need),
  or something Linux does pre-0.5 s that breaks a1 specifically.

## Next options (for CJ to order)

1. **Instrumented spmi-apple debug patch** (dev_info before/after the first
   `writel`/`readl` per controller): with serial printk now proven working,
   one boot pinpoints the exact stalling access. Needs a build + quick
   review (print-only patch).
2. **m1n1-side re-verification**: chainload the July-proven hpm2-status-r0
   object (re-pin its artifact first) to prove the a1 block still answers
   under m1n1 today — separates "Linux breaks it" from "the block changed".
3. **Offline RE of AppleSPMIController's a1/gen3 init path** (25F84 kexts):
   enumerate every MMIO write macOS performs on this controller before its
   first FIFO use; diff against our driver's nothing.
