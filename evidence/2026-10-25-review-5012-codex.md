# Codex second opinion on the 5012 fault-path TLBI retry diagnostic (2026-10-25)

Requested by claude through agent-bridge (`codex`, medium tier = gpt-6.1-sol, reasoning low), answer-only. It reviewed the FIRST draft (two stages: local, then broadcast). Verdict: **fix first**. Applied in the revised patch: a raw-spinlock-protected global state keyed on (CPU, PC, VA) instead of per-CPU VA alone; a global retry budget of 32; `*_bad` checks on the intermediate descriptors; PA decoded from the PTE printed beside `__pa`; PTE_CONT flagged; a new **stage 1 plain retry with no TLB maintenance** as the timing control; and weaker readout wording (recovery only counts if the workload progresses; AGAIN does not exclude every TLB-maintenance defect). Codex confirmed that the hook is reached (kworker, no mm, then no_context, then __do_kernel_fault, after fixup_exception; the spurious-translation and MTE checks do not consume FSC 0x0f), that returning retries the instruction, that the 16K/47-bit walk with folded p4d is valid, and that broadcast TLBI needs no IPI, so it is safe with IRQs masked.

## Full answer (codex)

- **1. Reachability and retry: correct for the stated fault.** In `arch/arm64/mm/fault.c`, a kworker with `current->mm == NULL` goes through `no_context` to `__do_kernel_fault()`. Your hook runs **after `fixup_exception()`**: an exception-table-covered access is fixed up first, but ordinary kernel `memcpy` normally has no such fixup. `is_spurious_el1_translation_fault()` rejects permission faults, so it will not consume `0x9600004f`. MTE tag faults have a different FSC and fail your permission-fault predicate; inserting before the MTE check is fine. Returning without changing `regs->pc` correctly retries the faulting instruction on exception return. A partly completed store sequence may repeat stores; ordinary RAM `memcpy` tolerates that.

- **2. Page-table walk: correct geometry, incomplete validation.**
  - With 16 KiB pages and 47-bit VA, the three hardware levels are L1/L2/L3; generic p4d and pud folding makes this traversal valid. `pud_leaf()` and `pmd_leaf()` are appropriate for rejecting block mappings. Rejecting PMD blocks is a coverage limitation, not a walk error.
  - `__ptep_get()` reads the raw descriptor once, which is useful here, especially for inspecting contiguous mappings.
  - `!PTE_RDONLY` means **the leaf AP bits permit writes** under ordinary permission handling. It is not the same predicate as Linux `pte_write()`, which tests `PTE_WRITE`/DBM. Conversely, `PTE_RDONLY | PTE_DBM` can represent a logically writable, clean mapping eligible for hardware dirty-state update; your “genuinely read-only” comment is too strong.
  - A writable leaf does **not establish effective writability**: hierarchical table permissions and enabled permission overlays can restrict access. The walk also lacks `*_bad()`/table-type checks and a final page-descriptor type check; malformed nonzero entries can be followed or accepted. Add those checks and capture ancestor descriptors. The unlocked snapshots do not protect against concurrent table replacement; that is tolerable only with an explicit stable-linear-map assumption.
  - `__pa(addr)` prints the expected linear-map PA, **not the PA decoded from the observed PTE**. Print both to detect a mapping mismatch.

- **3. Exception-context safety: the TLBI operations are suitable; CPU pinning is missing.**
  - `local_flush_tlb_all()` uses local TLBI plus barriers; `flush_tlb_all()` uses broadcast TLBI plus completion barriers. **Broadcast TLBI does not require IPIs or remote IRQ handlers**, so masked interrupts do not inherently deadlock it. Holding ordinary locks does not itself prohibit either helper.
  - Under genuine VHE host operation, these EL1-named maintenance operations target the host EL2&0 translation regime. Verify the actual boot mode, rather than inferring it from the helper names. See the regime selection in [Arm’s architecture specification](https://support.arm.com/documentation/ddi0487/mc/-Part-C-The-AArch64-Instruction-Set/-Chapter-C5-The-A64-System-Instruction-Class/-C5-5-A64-System-instructions-for-TLB-maintenance/-C5-5-54-TLBI-VAAE1IS--TLBI-VAAE1ISNXS--TLB-Invalidate-by-VA--All-ASID--EL1--Inner-Shareable?lang=en).
  - **A kernel abort does not guarantee preemption is disabled throughout this handler.** Entry can restore the interrupted IRQ state. Separate `this_cpu_*()` operations therefore need explicit CPU pinning across state selection, logging, and TLBI; otherwise migration can mix CPU records or flush a different CPU.
  - `pr_emerg()` is usable in atomic contexts, but synchronous console output can stall, encounter console-lock dependencies, or recurse. Its timing perturbation is substantial. Prefer deferred logging and minimal work before TLBI.

- **4. Retry accounting is not bounded per experiment.** In `t6040_205_stale_tlb_retry()`, `last VA + stage` only bounds consecutive matching faults **on one CPU**:
  - Alternating A/B faults continually reset stage 1; migration can restart the sequence or encounter another task’s old state.
  - After a successful retry, state remains armed. A later unrelated fault at that VA can be labelled “after local TLBI” or “AGAIN.”
  - Matching only FAR also conflates different instructions and tasks accessing the same address.
  
  Use an explicit experiment identity—at least task, PC, VA and originating CPU—and a **global bounded retry budget** that cannot reset on a different VA. Log intervening faults/migration and treat them as inconclusive. Pinning inside the helper alone does not prevent migration between exception return and the retried instruction. Without these changes, the diagnostic can repeatedly suppress real failures and its stage labels can be false.

- **5. Readout: useful evidence, but the proposed causal conclusions are too strong.**
  - **Stage-1 recovery:** consistent with stale local translation state; it does not prove a stale private leaf TLB entry. These operations also invalidate cached intermediate translations. Barriers, delay, concurrent PTE changes, dirty-state updates and logging-induced timing changes can yield the same apparent recovery.
  - **Stage-2 recovery:** establishes recovery after a subsequent broadcast attempt, provided retry identity is trustworthy. It does not establish that *only* broadcast works: you have also added time, another retry and stronger barrier scope. A repeat-local control is needed. A stale entry solely on another CPU cannot directly explain this CPU’s abort.
  - **AGAIN:** means this sequence did not clear the symptom. It does **not** exclude translation-maintenance defects: bad scope/regime, refilling stale state, concurrent modification, or defective TLBI completion remain possible.
  - **DBM/contiguous details:** DBM does not explain a stable ordinary leaf permission fault when AP[2] is already clear, but hardware dirty updates can race the software snapshot. With `PTE_CONT`, one raw descriptor cannot establish consistency of the whole contiguous group; capture that group if set. Walk-cache state and speculative refills also prevent identifying a specific private TLB structure.
  - There is **no explicit success observation** here. Absence of another fault is only “no recurrence observed,” unless a workload completion marker demonstrates progress. Use that wording and retain a no-TLBI retry control.

**Verdict: fix first — pin CPU-local operations, enforce a global retry bound with trustworthy fault identity, validate table descriptors, and weaken the success/causality claims.**
