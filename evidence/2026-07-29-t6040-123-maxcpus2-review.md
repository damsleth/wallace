## The patch does exactly what the ticket claims

Single file, `drivers/tty/apple_dockchannel_tty.c`, guarded by `CONFIG_SERIAL_EARLYCON`:

```c
static void apple_dctty_early_putchar(struct uart_port *port, unsigned char c)
{
	if (!readl_relaxed(port->membase + APPLE_DCTTY_DATA_TX_FREE))   /* 0x14 */
		return;                                                  /* drop, never wait */
	writel_relaxed(c, port->membase + APPLE_DCTTY_DATA_TX8);         /* 0x04 */
}
```

One `TX_FREE` read per byte, immediate drop when full, one `TX8` write. **No** RX, IRQ, mask,
config, or new register offset; bails out if `membase` is unset. `EARLYCON_DECLARE` only. The
earlycon address in the bootargs (`0x50882c000`) is the DockChannel **data** window established by
ticket 062, not the mailbox node's IRQ resource — correct, and ADT-derived.

`initcall_blacklist=apple_dctty_init` keeps the regular TTY driver from becoming a second owner of
that FIFO, which is why the reporter uses `/dev/kmsg` + `keep_bootcon` rather than a tty.

## DT isolation verified, not assumed

- **15 `cpu@` nodes, and `cpu@10105` carries `status = "disabled"`** → 14 usable cores, matching the
  recorded topology.
- **No `pcie@` node at all** (0 matches), so today's PCIe work cannot influence this result.
- `nvme@40dcc0000` disabled; all three `usb@` controllers (`382280000`, `38a280000`, `392280000`)
  disabled; 7 of 8 `iommu@` nodes disabled (the survivor is the DockChannel/HID DART the keyboard
  needs).

So "storage-disabled" is a property of the **DTB**, not the config — the kernel does carry
`PCI/SCSI/BLK_DEV_SD/USB=y`, but the DT gives them nothing to bind to. Consistent with tickets
067/071.

## Reporter is bounded and read-only

Mounts proc/sys/dev, arms the watchdog, then prints `cpu_{possible,present,online}`, the
`/proc/cpuinfo` processor count and implementer/part lines, and — the part that actually proves
something — runs `taskset -c 1` so a *second* core must execute, before emitting
`T6040_SMP_EARLY_RESULT_PASS` or `_FAIL` and a bounded 40-line dmesg grep. Then it sleeps forever;
no reboot, no retry, no escalation.

## Evidence channel: the panel, so no re-enrollment is needed

The obvious problem is that `earlycon=dockchannel` is read over KIS, and KIS cannot attach while the
newly enrolled dual-mode object's 10 s window owns the DFU-port gadget — `debugusb-console.sh reboot`
now reaches `Timed out` / `Valid payload found`, never `Running proxy`.

That does **not** block the run. `scripts/t6040-boot-dcuart.sh`'s base cmdline already contains
`console=tty0`, and the reporter writes to `/dev/kmsg`, so printk fans the whole report out to every
console — including the panel. The plan is therefore: catch the enrolled object's 10 s gadget window
to chainload, and read `T6040_SMP_EARLY_RESULT_{PASS,FAIL}` on the panel. No 1TR trip, no rollback
re-enrollment.

`maxcpus=2` is appended via `EXTRA_BOOTARGS`, which lands after the base `maxcpus=1`; the kernel
takes the last occurrence.

## Bounds for the run

Storage-disabled DT, one boot, no retry. If secondary bringup hangs there is no console output past
the earlycon banner and the m1n1 watchdog warm-resets in ~20 s — the same recovery every prior
DockChannel experiment used. Do not retry ticket 005 unchanged.
