## The delta (`f8aec6e` → `2877767`, init only; checker and launcher unchanged)

1. **`nvmeend=` parsing.** Accepted values `reboot` or absent; anything
   else stops before the gates. Correct, same shape as `nvmewc`.
2. **VolumeFlags log line**, both modes, after the geometry pins:
   `dd if=$DEV bs=1 skip=106 count=2 | od -An -tu2`, last field. Read-only
   (`dd if=`), bytes 106..107 are the exFAT VolumeFlags field the geometry
   pin deliberately skips, and the little-endian u16 decode is right (bit 1
   = VolumeDirty). I ran this BusyBox under arm64: `od -An -tu2` on
   `02 00` prints `2`, on `00 00` prints `0`, exit 0, so the line will
   carry a value rather than the empty string a missing `-t` would give.
   The line is informational; nothing branches on it.
3. **`nvmeend=reboot` after the PASS line only.** `sync`, then
   `reboot -f`, then a 30 s sleep and `park` if the reboot did not happen.
   The `reboot` applet is in the binary and its usage lists `-f`
   (bypass init, direct `reboot(2)`), which is what a BusyBox-PID1 image
   needs. Kernel side, verified in the tree: `reboot(2)` →
   `kernel_restart` → `kernel_restart_prepare` → `device_shutdown`
   (`kernel/reboot.c:100-105`) → the platform driver's `.shutdown` =
   `apple_nvme_shutdown` (`drivers/nvme/host/apple.c:1754,1835`), which
   runs `flush_delayed_work(&anv->flush_dwork)`,
   `apple_nvme_disable(anv, true)` → `nvme_disable_ctrl(ctrl, shutdown=true)`
   (`core.c:2682`: sets `CC.SHN = NORMAL`, waits for `CSTS.SHST = CMPLT`
   with the controller's shutdown timeout), then `apple_rtkit_shutdown` and
   clears `APPLE_ANS_COPROC_CPU_CONTROL`. So the test exercises exactly the
   path the daily driver's clean shutdown would take; whether ANS honours
   `CC.SHN` by committing its cache is the measurement.

Ordering is right: the exFAT volume is unmounted before PASS, so no
filesystem is live at reboot; the PASS line (and the checker's inputs) are
already on the console before `sync`/`reboot -f`.

## Notes

1. **Expect a logged `Deferred flush failed` at shutdown.** `flush_delayed_work`
   runs `apple_nvme_flush_work` (`apple.c:1515`), i.e. an NVMe Flush, which
   this firmware rejects (5006, run 1). It is logged and ignored; it is not
   a STOP condition for the checker (the pattern list has no `Deferred
   flush`), and it must not be read as the reboot having failed.
2. **If `CC.SHN` is never acknowledged**, `nvme_disable_ctrl` times out
   after `shutdown_timeout` (several seconds), logs, and the shutdown still
   proceeds to the RTKit shutdown. The verify boot will then show whether
   the cache was committed anyway. Capture the console through the reboot;
   the `nvme nvme0: ... shutdown` / timeout line is the evidence for which
   of the two happened.
3. **Checker and launcher.** Neither knows about `nvmeend`; the launcher's
   PASS detection fires before the self-reboot, so it runs the checker as
   before and does not issue its own `macvdmtool reboot`. The verify boot
   for r3 must pass `nvmewritedir=r3` (same TAG) and should pass
   `nvmewc=through` again so the verify's own mount metadata behaviour
   matches the write run. Add the `VolumeFlags=` and the `clean kernel
   reboot:` lines to the run evidence; the checker does not require them.
4. **Not flow-tested**: unlike 5003b, the two new lines have no loop
   regression (a `reboot -f` cannot be loop-tested). The `od` decode is
   covered by the arm64 run above; the reboot path is covered by source.
5. Still carrying the unused `sbin/nvme-readonly-test`.
