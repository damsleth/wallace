# Codex review of m1n1 patch 0004 (TrustCache reservation, ticket 5015), 2026-10-31

Reviewer: codex medium via agent-bridge, from a copy of the post-patch
`kboot.c`. Verdict: **OK-with-changes**. Disposition by claude; no code change
taken.

- **Overflow before rounding** (`tc[0] + tc[1]`, `ALIGN_UP`). Not taken: the
  values are DRAM physical addresses from iBoot's own memory-map; neither can
  approach 2^64. The size and sentinel checks (16-byte read, size 0, all-ones)
  stay.
- **FDT reservations don't constrain m1n1's own placement.** Agreed in
  principle; not a problem here. The range ends at `adt_end + 0x60000`, which is
  exactly the m1n1 image base on every recorded boot (5012 boots a/b and the
  2026-10-30 live boot, stage 2 included). m1n1 allocates its heap, payload, DT
  and log buffer above `_end`.
- **Bail if TrustCache is missing on T6040.** Not taken: a hard boot failure is
  worse than running without the reservation, and the daily images stay at
  `maxcpus=1` until 5015's run matrix passes. The log line records the miss.
- **`/memreserve/` vs `no-map`.** Codex agrees `/memreserve/` is enough: the
  fault is on writes from secondaries, and a mapping alone does not cause it.
- **Chainload provenance.** The memory-map entry is iBoot's physical layout
  and is copied unchanged with the ADT. The live 2026-10-30 boot (stage 2
  `80badc91`) showed the same `adt_end + 0x60000` image base, so the layout holds
  through chainload.
