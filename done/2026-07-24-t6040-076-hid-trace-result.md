## Result — the auto-report captured cleanly (TX-only, no RX needed)

Alpine RAM-root reached a shell (`wallace-ramroot:~#`). The bounded report:

**DockChannel HID (`514b14000.mailbox`) — RX WORKS:**
`mode=irq irq=41 tx_mask=0x4 rx_mask=0x8; irq_calls=26 irq_wakes=19 rx_runs=19
rx_batches=13 rx_bytes=1396`. So the MTP/HID DockChannel delivers data via IRQ 41.

**DCHID (`514600000.hid`) — every interface created, ret=0:**
`stm id_ret=34 serial_ret=23 id=0x5ac:0x359:0x510; rx_callbacks=13 rx_bytes=1396
packets=19 cmd_packets=8 report_packets=11 acks=8 ack_matches=8 events=11;
init_seen=0x7e ready_seen=0x7c create_queued=0x7e create_ok=0x7e id_ready=1`.
Interfaces created: `multi-touch (1)`, **`keyboard (2) ret=0`**, `actuator (4)`,
`tp-accel (5)`, `mtp (6)` — all `ret=0`.

**But NO input device registered:** `/proc/bus/input/devices` **empty**;
`/dev/input` **[unavailable]** (dir absent). `/proc/partitions` empty (storage-free,
as intended).

**Console DockChannel (`50880c000.mailbox`, ttydc0):** `mode=poll rx_bytes=0` —
console RX still zero (the separate poll-mode-console issue; TX worked, hence the
report). Note this is a *different* dockchannel from the HID one (which RX-works
on IRQ 41).

## 077 boundary decode — DEFINITIVE

The regression is **downstream of DCHID interface creation, at HID-core → input
registration**:
- NOT a DockChannel RX race (the hypothesis 069/071 chased) — HID RX delivers
  1396 bytes over IRQ 41; the mask/drain/re-arm was correctly disproven by 071.
- NOT identity/interface creation — STM id/serial read, `id_ready=1`, and every
  iface incl. **keyboard** created with `ret=0`.
- The failure is that none of those HID devices become a Linux `input` device
  (`/proc/bus/input/devices` empty, no `/dev/input`).

Kernel config rules out the obvious gap: `CONFIG_INPUT=y`, `INPUT_EVDEV=y`,
`INPUT_KEYBOARD=y`, `HID=y`, `HID_GENERIC=y`, **`HID_APPLE=y`** are all built-in —
so the keyboard's binding driver is present. (`HID_MULTITOUCH=m` is a module
absent from the RAM initramfs, which would only block the *trackpad* iface, not
the keyboard.) Therefore the keyboard failing to register with `HID_APPLE`
built-in points to a **dockchannel-hid driver regression in the 7.1.3 base**: its
transport `create_ok` counter increments, but the call into the Linux HID core
(`hid_add_device`/`hid_hw_start`→`hidinput_connect`) does not produce an input
device. The working 2026-07-11 keyboard used an earlier kernel; something in the
dchid registration path regressed between then and 7.1.3.
