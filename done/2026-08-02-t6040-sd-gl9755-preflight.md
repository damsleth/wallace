review. It carries the proven T6040 PCIe path and only the already-approved SD
reader endpoint-power key, SMC `gP19`, through upstream `gpio-macsmc`. It does

## Ticket A — read-only smoke (199)

Ticket 193 completed a separate combined read/write/persistence run while this
offline work was in progress, proving the hardware path on another image. The
hash-pinned ticket 199 is the stricter staged follow-up requested here: read
and write remain separate approval boundaries. After independent review and
CJ approval, acquire the lease, establish a fresh `Running proxy`, and boot
exactly (once per power cycle):

```sh
scripts/rig-lease.sh acquire sol "ticket 199 GL9755 read-only smoke" bd3dd526
RIG_AGENT=sol M1N1_BIN=/Users/damsleth/Code/linux-build-out/m1n1-t6040-pcie-V1-upstream-04e8829c.bin \
  IMAGE=Image-sd-gl9755 \
  bash scripts/t6040-boot-dcuart.sh \
    t6040-j614s-dcuart-sd.dtb initramfs-alpine-sd-smoke.cpio.xz
```

Then, only after the shell is visibly alive:

```sh
printf '/usr/local/sbin/t6040-sd-readonly-smoke\n' > /tmp/m1n1
```

Pass requires: `17a0:9755` bound to `sdhci-pci`, an IOMMU group, `mmcblk0p1`,
`LABEL="SD64"`, `TYPE="exfat"`, a mount whose `/proc/mounts` options contain
`ro`, directory listing, SHA-256 of one pre-existing regular file, clean
unmount, and no PCIe/DART/kernel fault signature. Stop without mounting on a
fault, missing/wrong card, wrong label/type/driver, or missing partition. Stop
after unmount failure, non-RO options, or no file. Ticket A performs no write,
fsck, repartition, reformat, or raw block access.

## Optional follow-on: SD as untethered stage-2 storage

Flag only; do not build yet. U-Boot already has Apple PCIe and generic
SDHCI-PCI support, so an SD stage-2 path is plausible once Linux proves the
same GL9755/card path, but U-Boot has no exFAT support: the present SD64
fixture would need a FAT32 partition or a separate FAT32 card, and creating
that partition is explicitly outside these tickets. SD would offer removable,
low-risk stage-2 iteration without depending on the internal ANS queue-wrap
work, but it adds a card-presence dependency and consumes the reader; the
ticket-191 NVMe stage-2 design is physically internal and the better eventual
daily-driver route if the NVMe CQ-wrap blocker is solved. Keep both as design
options, ask CJ before any partition change, and do not let this follow-on
expand tickets 199/200.
