# SMP: all 14 cores enter the kernel on the M4 Pro (tickets 123 + 121)

> **Scope correction (2026-07-29, after CJ challenged the claim).** The title previously read "all 14
> cores come up", which overstates the evidence. What is proven is that **all 14 cores enter the
> kernel and SMP bringup completes**. What is NOT proven, and has never been observed: a shell running
> with 14 cores online. `cpu_online` was read from sysfs only at `maxcpus=2` (`0-1`), and a task has
> only been *proven to execute* on CPU 1. Cores 2-13 have never had work scheduled on them, and the
> one `maxcpus=14` boot oopsed 30 ms after bringup on an unrelated (self-inflicted) initramfs fault.
> Read every "14 cores" statement below as "14 cores entered the kernel".

2026-07-29, over KIS with the rollback loader enrolled. Two results, one on each of the two boots.

## Ticket 123 — maxcpus=2: PASS

Exactly the reviewed artifacts (m1n1 `1394c345`, `Image-dcuart-earlycon`, DTB `2782b922`,
initramfs `43944ef2`), bootargs appended as specified:

```text
cmdline: … ignore_loglevel maxcpus=2 earlycon=dockchannel,mmio32,0x50882c000 keep_bootcon initcall_blacklist=apple_dctty_init rdinit=/init
cpu_possible: 0-13      cpu_present: 0-13
cpu_online:  0-1        processor_count: 2
processor 0: CPU implementer 0x61  CPU part 0x055
processor 1: CPU implementer 0x61  CPU part 0x054
cpu1_task_psr: 1
T6040_SMP_EARLY_RESULT_PASS
```

`cpu1_task_psr: 1` is the load-bearing line: a `taskset -c 1` task actually executed on CPU 1, so
this is real secondary execution rather than a core merely being counted. Note the two cores are
**different part numbers**, so bringup already crosses core types.

## Ticket 121 — maxcpus=14: all 14 entered the kernel, mapping confirmed; userspace never reached

Same artifacts, `maxcpus=14`. From the kernel itself:

```text
smp: Bringing up secondary CPUs ...
CPU1:  Booted secondary processor 0x0000000000 [0x611f0541]
CPU2:  Booted secondary processor 0x0000000001 [0x611f0541]
CPU3:  Booted secondary processor 0x0000000002 [0x611f0541]
CPU4:  Booted secondary processor 0x0000000003 [0x611f0541]
CPU5:  Booted secondary processor 0x0000010101 [0x611f0551]
CPU6..CPU8:                      0x0000010102..04 [0x611f0551]
CPU9:  Booted secondary processor 0x0000010200 [0x611f0551]
CPU10..CPU13:                    0x0000010201..04 [0x611f0551]
smp: Brought up 1 node, 14 CPUs
SMP: Total of 14 processors activated.
```

Decoding the MPIDRs and part IDs gives the topology **measured, not assumed**:

| cluster (MPIDR aff1) | CPUs | part | count |
|---|---|---|---|
| 0 | 1–4 | `0x054` | **4 E** |
| 1 | 0 (boot), 5–8 | `0x055` | **5 P** |
| 2 | 9–13 | `0x055` | **5 P** |

= **4E + 5P + 5P**, exactly ticket 121's expected mapping. m1n1's own FDT pass agrees and correctly
reports `FDT: CPU 9 is not alive, disabling...` for the extra `cpu@10105`.

**What is still unproven for 121:** the userspace half — `cpu_online: 0-13` from sysfs, pinned-task
liveness per cluster, and shell/watchdog stability — because userspace never started on that boot
(see below). The kernel's own count is strong evidence for core bringup; it is not evidence that all
14 are schedulable.

## Why userspace died, and it was self-inflicted

```text
[0.034272] Unpacking initramfs...
[0.034531] Unable to handle kernel write to read-only memory at virtual address ffff000005d84000
Internal error: Oops: 000000009600004f [#1]  SMP
  … deferred_probe_work_func / __device_attach …
```

The oops is in **initramfs unpacking**, and it happened with the two archives I repacked myself
(`initramfs-smp14-report.cpio.gz`, `initramfs-smp-kmsg-report-loop.cpio.gz`) — never with the
original `initramfs-smp-kmsg-report.cpio.gz`. Cause: I extracted the proven archive as a **non-root
user**, so its device nodes were silently skipped, then repacked the incomplete tree. The result
oopses the unpacker.

This also retroactively explains the earlier "Asahi logo, no text, then a reboot" on the panel, which
I mis-attributed twice (first to a stalled handoff, then to fbcon). The actual fbcon fact is separate
and worth keeping: `fbcon_init: detected unhandled fb_set_par error, error code -16` on this
kernel/DTB, so `console=tty0` renders nothing on the panel and KIS is the only usable channel here.

**Rule:** never repack a proven initramfs from a non-root extraction. Modify the source tree and
rebuild with the original builder, or do the extraction with `sudo`/`bsdtar -p` so device nodes
survive.
